## Verdict up front

**The floors hold and nothing fabricates.** The safety property TD-005 exists to
protect — an off-corpus question gets an honest miss, never an invented KB answer
— is intact 4/4 through the real `search()` path at 9.3× the corpus the floors
were fitted to.

**But the battery exposed a defect it was never designed to look for:** the S8
battery labeled the *neural leg*, and the leg is fine. What a user actually reads
is the **RRF-fused top hit**, which S8 never labeled. Labeled today, the definition
path renders the **wrong ATT&CK page for 3 of 7** true positives. Not a floor
problem — every hit involved is above the floor. See §4.

## 3. The cve floor is currently dormant — and one structural guarantee has eroded

Every KB retrieval caller in the tree (`grep` for `kb.search` / `kb.lookup_ids`):

- `auspex/routes/chat.py:372` — CVE questions → `lookup_ids`, the **exact-ID rail**
  (BM25 term match on the `ids` keyword field). No neural leg, so no neural floor.
- `auspex/routes/chat.py:383` — DEFINITION questions → `search(...,
  doc_types=("concept","technique","tactic"))`, the **curated pool only**.

So in v1 **nothing reaches the `cve: 0.70` floor**, and S8's "re-battery before any
unfiltered surface ships (none exists in v1)" still stands. The measurements above
are pre-calibration for a surface that does not exist yet, which is the right time
to take them.

**Erosion worth writing down:** S7/S8 established that "a `doc_types` filter makes
lucene kNN exact over a small subset — this restores recall, it doesn't just trim"
(quoted in `service.py:518-524`). For `doc_type=cve` that is **no longer true**:
cve is 96% of the corpus, so filtering to it is not a subset at all. Measured —
the filtered and unfiltered CVE batteries returned **byte-identical** results.
The property still holds for the curated filter (1,266 chunks = 4%), which is the
only filter v1 uses. A future CVE surface **cannot** inherit the recall argument
that justifies the curated one.

## 4. THE FINDING: the definition path renders the wrong page (3/7)

S8's battery labeled the neural leg. Users read `render_definition_answer(hits)`,
which renders `hits[0]` — the **fused** top — as *the* definition
(`auspex/kb/echo.py:164-171`). Labeled through the real path for the first time:

| query | renders as | wanted | assessment |
|---|---|---|---|
| what is credential access | TA0006: Credential Access | TA0006 | correct |
| what is process injection | T1055: Process Injection | T1055 | correct |
| living off the land binaries | CONCEPT-LOLBIN | CONCEPT-LOLBIN | correct |
| what is lateral movement | **TA0008: Lateral Movement** | CONCEPT-LATERAL-MOVEMENT | **stale label, not a defect** — TA0008 is ATT&CK's own page titled exactly "Lateral Movement" and is a fine answer. Same labeling trap S8 caught with the k8s query, in the opposite direction. |
| what is phishing | **T1598: Phishing for Information** | T1566 | **DEFECT** — T1598 is a reconnaissance sub-case; T1566 is *the* phishing technique, and it is not in the returned 5 at all |
| what is credential dumping | **TA0006: Credential Access** | T1003 | **DEFECT** — answers a technique question with its parent tactic; T1003 not in the returned 5 |
| how do adversaries abuse command line interpreters | **T1202: Indirect Command Execution** | T1059 | **DEFECT** — T1202 is about evading command-line logging |

All four off-corpus queries still return `None` → honest miss. **Nothing
fabricates.** This is a relevance defect, not a safety one.

### Mechanism (measured leg-by-leg, `diagnose_legs.py`)

**(a) RRF fragments a multi-chunk doc's vote.** `rrf_fuse` accumulates scores keyed
on `chunk_id` (`auspex/kb/fuse.py:64`). For *what is phishing* the neural leg
returns **three separate T1566 chunks** (ranks 2, 4, 5), each earning its own
modest RRF score and none combining, while T1598 sits at rank 0 in **both** legs
and accumulates `0.4/61 + 0.6/61`. A doc split across more chunks competes against
itself. RRF is being run over chunks while the *answer* is a doc.

**(b) BM25 omits the canonical page entirely.** T1566 is **absent from the BM25 leg**
for "what is phishing"; T1003 is **absent** for "what is credential dumping". Their
neighbours (T1598.*, T1555.*, T1556.*) saturate all 10 slots. So the canonical page
enters fusion with a single-leg vote at best.

**(c) Tactic pages out-score their techniques.** For "what is credential dumping",
TA0006 is rank 0 in *both* legs — the tactic page mentions the technique's name, so
it wins lexically and semantically, and answers at the wrong granularity.

### Two candidate fixes measured — neither is a clean win (thrash brake)

`variant_fusion.py`, all 7 positives:

| variant | correct definitions |
|---|---|
| baseline (ship today) | 3/7 |
| **A** — dedupe each leg to best-chunk-per-doc before fusion (one doc, one vote) | 3/7 |
| **B** — A + promote a doc whose title *is* the query subject | 4/7 |

Variant A is *principled* — it fixes mechanism (a) and is the standard
RRF-over-documents form — but on this battery it changes **nothing measurable**,
because mechanisms (b) and (c) dominate. Shipping it alone would be unmeasured
churn. Variant B additionally fixes only *what is phishing*, and its stopword list
is the kind of hand-tuning that rots.

Per CLAUDE.md rule 7 (two failed approaches on one problem → stop, write it down,
move on), **no fix shipped this session.** Logged as **TD-026** with these numbers
so the next attempt starts from measurement rather than from scratch.

**Harness note (a false finding I nearly recorded):** `variant_fusion.py`'s
honest-miss check reported "LEAK" for two negatives. That was my harness fusing
the legs directly and skipping `search()`'s `if not neural: return []` disagreement
rail (`service.py:539-545`). Verified against the real path: for those queries the
neural leg post-floor is **0 hits** while BM25 returns 1 and 6 — the rail is
exactly what converts leg disagreement into the honest miss, and it works.

## 5. The SharePoint "recall miss" is honest crowding, not HNSW collapse

`SharePoint deserialization remote code execution` → CVE-2026-58644 was HIT@1 at
S8 and is **absent at k=10** now. Not a recall failure:

- Its score is **0.7660 — identical to S8's 0.766**. The doc is still indexed
  (verified by term query) and still well above the 0.70 floor.
- It sits at **rank 22**, stable at k=50 *and* k=100 — an HNSW recall collapse
  would be unstable across k, which is how S7's collapse presented.
- The 21 chunks above it are overwhelmingly genuine Microsoft SharePoint/Office
  RCE CVEs (CVE-2021-34468/34520/34467, CVE-2022-41062, CVE-2024-30052 …) that the
  corpus simply did not contain at 2k chunks.

The *label* is what went stale: at 2k chunks this query had one right answer, and
at 30.5k "the SharePoint deserialization RCE" is under-specified. Recorded rather
than "fixed" — the corpus decides what is off-corpus, not the test author (S8's own
lesson).
