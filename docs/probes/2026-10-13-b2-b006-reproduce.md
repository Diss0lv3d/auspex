## The runs (3, each a fresh chat)

1. "what do you know about this IP: 34.187.179.218" took the IOC check
   (shortcut, no model). It answered "no signal from 5 connected sources" and
   gave the network line (AbuseIPDB: Google LLC …).
2. "dig deeper" ran in mode **general**, agent path, 2 calls.
   - It made one `enrich_observable(34.187.179.218)` call, which the model
     read as:
     ```
     {"results": [{"observable": {"id": "ipv4-84ed934c", "type": "ipv4", "value": "34.187.179.218", "defanged": false}, "sources_answered": 5, "signals": [], "network": [{"source": "AbuseIPDB", "summary": "Google LLC (google.com), Data Center/Web Hosting/Transit, US · hostname 218.179.187.34.bc.googleusercontent.com"}]}], "recorded": true}
     ```
   - **Every answer called the address clean** (3/3), using the words
     "clean", "safe", "legitimate" and "no malicious". From run 1:
     "**Clean reputation**: The IP has no known threat associations …",
     "**Risk Level**: Low", "This appears to be safe Google infrastructure",
     and "The absence of any threat intelligence signals across multiple sources
     is a strong indicator that this is not a malicious IP address."

**A first attempt was invalid and was overwritten.** The probe had not turned
enrichment on, so every turn 2 read `enrichment_inactive`. The model then said,
honestly, that it could not look the address up. That is not B-006's
condition.

## Root cause

Two gaps, and the turn falls through both.
- **The data.** For an indicator that sources answered for and none
  signalled, the agent's tool result carries a bare `"signals": []` beside
  `"sources_answered": 5`. Nothing in it says what that means.
  - The payload's own comment covers the other case: an indicator that was
    not looked up gets `not_checked`, "because a model given 'no signals'
    would call it benign" (`auspex/agent/capabilities.py:300-303`).
  - Looked up with no signal, it says nothing, and the model calls it benign.
- **The mode.** "dig deeper" resolves to `general` (the resolver reads only
  the current message). general's directive does not carry ioc_enrichment's
  hard rule, "Never assert a reputation verdict you do not have evidence
  for; absence of data is 'unknown', not 'benign'" (`auspex/modes/catalog.py`).

Burhan's call: fix both, in code and in the prompt.
