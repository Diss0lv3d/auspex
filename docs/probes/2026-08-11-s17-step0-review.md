## A. The digest read the whole archive to find what crossed a band

TD-021 said this read was the only new one in three sessions without an asserted
plan. It was right to say so.

**Setup:** 98,976 observables / 108,952 verdicts in one workspace, three
half-life families (14 d / 30 d / 365 d), ages spread over two years, `VACUUM
(ANALYZE)` first. Default window (`days=7`), page of 50.

**Before — 143 ms median** (`EXPLAIN (ANALYZE, BUFFERS)`):

```
Limit  (actual time=150.333..154.967 rows=50 loops=1)
  Buffers: shared hit=221560, temp read=2394 written=3006
  ->  Nested Loop Semi Join
        Rows Removed by Join Filter: 68236
        ->  Gather Merge  (actual rows=22762)
              ->  Sort
                    Sort Method: external merge  Disk: 6200kB      <-- spilled
                    ->  Hash Join
                          ->  Parallel Seq Scan on observables o
                          ->  Subquery Scan on l  (actual rows=98976 loops=2)
                                ->  Index Scan using idx_verdicts_ws_obs
                                      (actual rows=108952 loops=2)  <-- all of it
Execution Time: 156.010 ms
```

It materialised the latest verdict for **every** observable, threw 68,236 of
them away in the join filter, and sorted the survivors **on disk**. Cost was the
size of the workspace's history, not of the handful of rows that crossed a band —
on the page an analyst opens FIRST after a week away.

### The algebra that makes it indexable

The predicate was never the problem; its spelling was. For band edge `e`:

```
crossed e in (since, now]
  <=> (now - created_at) >= e*hl  AND  (since - created_at) < e*hl
  <=> since - e*hl  <  created_at  <=  now - e*hl
```

Moving `created_at` to one side turns the crossing set into a **`created_at`
range per (edge, half-life) pair, exactly as wide as the window itself**,
whatever the half-life. Ranges use an index; an expression over
`half_life_days` cannot.

Two things had to be true for that to be safe:

1. **The half-lives come from the DATA, not a parameter.** Passing
   `HALF_LIFE_DAYS` in would have been shorter and would have made a verdict
   written with an uncovered half-life *silently absent* from the digest — the
   exact failure class S16 Step 0 spent itself on, on a surface whose whole
   subject is absence claims. A recursive loose-index-scan enumerates the
   families actually present: **3 values in 14 buffers, `Heap Fetches: 0`.**
2. **`OFFSET 0` is load-bearing.** Two intermediate attempts are recorded here
   because the second looks correct and is not:

| Shape | Median | Why |
|---|---|---|
| original | 143 ms | whole history + disk sort |
| ranges as a plain `JOIN` | 100 ms | planner flattened it, hash-joined the table, range became a *join filter* (`Rows Removed: 325,560`) |
| ranges via `JOIN LATERAL … ON TRUE` | 71 ms | still pulled up — LATERAL alone is not a fence |
| **`JOIN LATERAL … OFFSET 0`** | **4.6 ms** | 9 parameterised index range scans, 144 rows each |

**After — 4.6 ms median, 33×:**

```
->  Index Scan using idx_verdicts_ws_hl_created on verdicts v
      Index Cond: ((workspace_id = …) AND (half_life_days = hl.half_life_days)
                   AND (created_at > …) AND (created_at <= …))
      (actual time=0.003..0.041 rows=144 loops=9)
->  Index Scan using idx_verdicts_ws_obs  (actual time=0.001 rows=1 loops=1296)
->  Index Scan using observables_pkey     (actual time=0.001 rows=1 loops=1184)
Execution Time: 4.982 ms
```

No sequential scan, no temp files, 11,494 buffers instead of 221,560.

### Equivalence, and the one place it is a wash

Old and new compared on **full, unbounded result sets** at every window size, on
the same 99k rows:

| days | rows | identical | old | new | speedup |
|---|---|---|---|---|---|
| 1 | 172 | ✅ | 149.3 ms | 0.94 ms | 159× |
| **7 (default)** | 1,184 | ✅ | 142.9 ms | 4.44 ms | **32×** |
| 30 | 4,770 | ✅ | 144.3 ms | 18.76 ms | 8× |
| 90 | 11,082 | ✅ | 150.0 ms | 49.98 ms | 3× |
| 365 (max legal) | 32,930 | ✅ | 134.1 ms | 146.33 ms | **0.9×** |

**Logged honestly:** at the widest legal window the rewrite is ~9% slower. The
crossing ranges are then 365 days wide, so the candidate set stops being a thin
slice and the per-candidate "is this still current?" descent stops paying for
itself. The crossover is somewhere near 300 days. Kept anyway: 7 days is the
default and the reason the page exists, and a 365-day digest is dominated by the
32,930 rows it finds rather than by the query (see E).

Also verified: a superseded verdict that crossed an edge is reported by neither
version (only the current verdict can go stale), and a verdict crossing two
edges inside one window is reported once, naming the outermost transition.

**Fix:** new index `idx_verdicts_ws_hl_created (workspace_id, half_life_days,
created_at)` + the rewritten `_DECAYED_SQL`. Pinned by a plan assertion at 25k
rows (the size the S14/S15 suites use) and by semantic tests at the same scale.

## B. Derived-link fan-out across different kinds — SOUND

The read-time LATERAL takes `ORDER BY satisfied_at DESC, id LIMIT 1`, and S16
only pinned two verdicts of the SAME kind. The different-kinds case is real, not
hypothetical: `derive.conditions_for` gives a non-malicious CVE verdict **both**
`kev_listing` and `record_withdrawn`, so a CVE that is KEV-added and later
withdrawn with no re-enrichment between produces two matches and two satisfied
claims sharing one doc id.

Executed through the real `satisfy_documents` and `list_matches`:

```
satisfied kev-added: moved=1
satisfied deleted:   moved=1
match change_kind='deleted'
  falsifies: 'This verdict rests on the published record for CVE-2021-444555.'
match change_kind='kev-added'
  falsifies: 'CVE-2021-444555 is not known to be exploited in the wild.'
one-to-one pairing: kev=True withdrawn=True distinct=True
```

The pairing holds because the LATERAL matches on `satisfied_change_kind =
m.change_kind` as well as workspace/observable/doc. Neither event borrows the
other's claim. No change made.

## C. Two clocks decided one band — real, small, fixed by construction

`created_at` is `clock_timestamp()` in Postgres; `now` defaulted to
`datetime.now(UTC)` in the app process. Nothing checked they agreed.

Measured magnitude, same row read three ways:

```
postgres clock_timestamp(): 2026-08-10T22:49:26.943885+00:00
app datetime.now(UTC):      2026-08-10T22:49:26.944411+00:00
measured skew on THIS host: 0.001s

in sync          half_lives=0.0     conf_now=0.7     band=fresh
app 2 days FAST  half_lives=0.005   conf_now=0.6973  band=fresh
app 2 days SLOW  half_lives=0.0     conf_now=0.7     band=fresh   (clamped)
```

So a two-day skew moves a 365-day verdict by 0.005 half-lives and **no band
moves**. This is not a bug being fixed; it is a question being removed. The
digest's window was the more interesting half — both ends of it were app-derived
while the rows were not, so a skewed container slid the whole window.

**Fix:** `timeline.store.reader_now()` — the default `now` is
`SELECT clock_timestamp()`, and the digest route derives both ends of its window
from it. The clock that stamps a row is the clock that ages it. Callers passing
an explicit `now` (every test) still decide for themselves.

## D. A pristine checker roster could not tell quiet from dead

The lead was right, and there are two distinct holes.

```
long-lived process, 5 failed cycles:
  watchers   consec=0 degraded=False ever_succeeded=False
  fanout     consec=5 degraded=True  ever_succeeded=False
  trustworthy=False                                   <-- works

crash loop, process restarts after every 2 failed cycles:
  restart 0: fanout(consec=2,degraded=False)  quiet=True trustworthy=True
  restart 1: fanout(consec=2,degraded=False)  quiet=True trustworthy=True
  restart 2: fanout(consec=2,degraded=False)  quiet=True trustworthy=True

fresh process, zero cycles run:
  quiet=True trustworthy=True ever_succeeded=[False, False]
```

* **D1 — nothing has run yet.** A freshly started process reports every checker
  at zero failures, and zero failures out of zero attempts was being read as
  health.
* **D2 — the count forgets across restarts.** A crash-looping app fails its check
  every single cycle and never reaches `DEGRADED_AFTER`, because the counter
  resets before it gets there. Every cycle failed; the digest reassured anyway.

**The obvious fix does not work.** Requiring `ever_succeeded` would false-alarm
in a genuinely quiet week, because a consumer records success only when a
relevant change arrives — and `scheduler.py` guards **every** `emit()` on a
non-empty doc list, so a cycle with nothing to do never reaches a counter at all.
`FanoutSink` would record a success on `emit([])`, but nothing ever calls it that
way. There was no signal in the system meaning "a cycle ran".

**Fix, three parts:**

1. `IngestScheduler` gains a `FailureCounter("ingest-cycle")`, always on the
   roster, recording success when a cycle completed with both phases intact and
   a failure when one raised. A cycle skipped for a dead KB records **neither** —
   it looked at nothing, and calling that success is the laundering the counter
   exists to stop.
2. `Digest.trustworthy` additionally requires that *something* has succeeded in
   this process (closes D1).
3. A checker whose only evidence in this process is failure is untrustworthy at
   the **first** failure (closes D2). `DEGRADED_AFTER` exists to tolerate a bad
   batch among successes; with no successes there is nothing to tolerate it
   against. `CheckerStatus.degraded` is left alone — it stays the breaker-shaped
   fact it always was, and the judgment lives in the property that makes the
   claim.

**Still not caught (→ TD-022):** a checker that succeeded and then stopped being
run at all. `ever_succeeded` never expires, so a scheduler task that dies after
a week of health leaves a roster that reads clean. That needs a heartbeat with a
timestamp, durable across restarts.

## E. A truncated digest read exactly like a complete one

Found while measuring A: `days=365` returns **32,930** decayed verdicts and the
page shows 50.

```
matches in DB for this window: 2
returned with limit=1:         1
payload keys: ['bands','checkers','contradicted','decayed','flipped','note',
               'now','quiet','reopened','since','trustworthy']
truncation signal in payload: NONE
```

The page then rendered `d.decayed.length` as the count in its banner — so a
digest cut at 50 announced "50 went stale" when 32,930 had. This is the same
failure as an unexplained empty list, which this surface already refuses to
make: a bounded answer presented as a complete one.

**Fix:** each list is fetched at `limit + 1` and trimmed — no `COUNT(*)` over the
archive, and never a total the page cannot back up. `Digest` carries `limit` and
`truncated`; the payload adds `limit`, `complete` and `truncated` (translated
into the names the payload gives those lists, since `matches` is rendered as
`reopened` — a flag naming a key the client cannot find would be worse than no
flag). The page states truncated counts as "at least N" and marks each cut
section.
