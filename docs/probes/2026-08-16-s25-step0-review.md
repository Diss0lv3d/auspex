## The measurement discipline — sixth session

The rule (assert the REASON, make controls ARITHMETIC) was applied up front this
time rather than caught after the fact. `probe_resolve_drop.py` asserts, before
calling anything, that the shared extractor finds exactly 3 observables in the
subject string and exactly 1 in the control — so a result of "1 resolved" cannot
be blamed on the input. It carries a second control (**C2**) that passes the same
three indicators as three separate items and asserts 3 come back, which is what
proves the loss is the per-string collapse rather than a limit of `_resolve`.

The same shape is in the shipped tests: each asserts `len(_obs(input)) == 3`
before exercising the tool.

**This is not a claim that the discipline is fixed.** It was applied here; five
consecutive sessions found it broken somewhere. Read this section next session too.

## FIXED 1 — one argument holding three indicators was answered about one

**Read first.** `_resolve` did `found = parsed[0] if parsed else None` — the first
observable extracted from each argument item, the rest discarded. Nothing counted
them, and `unresolved` only ever received strings that parsed to *zero*
observables, so a partial answer was indistinguishable from a complete one.

**Then measured** (`probe_resolve_drop.py`):

| case | input | expected | measured |
|---|---|---|---|
| C1 control | one string, 1 observable | 1 resolved | 1 resolved |
| C2 control | 3 strings, 1 each | 3 resolved | **3 resolved** |
| S1 | 1 string, 3 inside | ? | **1 resolved, 2 lost, `unresolved` empty** |
| S2 | bare string via `_as_list` | ? | **1 resolved, 2 lost** |
| S3 | `"8.8.8.8, 1.1.1.1, 9.9.9.9"` | ? | **1 resolved, 2 lost** |

C2 is the control that matters: `_resolve` *can* return three, so the loss is the
per-string collapse.

**Why it is worse than an inconvenience.** The analyst asks "check these three".
Two are never sent to a provider, the payload says nothing, and the model writes
an answer that reads as if it covered all three. That is *not-checked* rendering
as *no-signals* — which this module's own docstring calls "the whole of the
DEFERRED rail" — and the module separately promises in words that strings are
"returned separately and reported, **never dropped**".

**Reachability, honestly.** Measured live against Scout (see the tool-choice
record): it sends **three separate array items** for "check these three", so this
is **latent on the endpoint we have, not unreachable**. It stays a defect because
`_as_list` exists specifically to accept a bare string ("models send a bare string
where an array is specified often enough that treating it as a contract violation
would fail turns"), and a bare comma-separated string arrives as ONE item —
measured above as S3. Same argument that ratified S24's per-channel carry fix:
the switch count, or the argument shape, is a property of the **endpoint**, and the
platform's premise is whatever endpoint the customer brings.

**Fixed** (`d47adea`). Every observable a string yields is kept, bounded by
`MAX_TOOL_ARG_ITEMS` — the existing argument boundary widened to cover what the
strings *yield*, not a second calibrated number (the standing "reuse caps, never
re-declare" rule; S24 nearly shipped a second copy of `ENRICH_MAX_OBSERVABLES`).
Overflow is named as `omitted_observables`, kept **distinct** from `omitted`,
because "you sent too many strings" and "your strings held more indicators than we
will check" are two different sentences. Over-cap indicators past the enrichment
service's own cap keep arriving as `CAP_SKIP`, unchanged.

**Proven to fail pre-fix** by truncating the parse to `parsed[:1]`: exactly the 3
new tests fail, the other 30 stay green.

## FIXED 2 — a bare number in a tool argument raised, and the model learned nothing

**Read first.** `items = [raw] if isinstance(raw, str) else list(raw)`. A model
sending `{"observables": 5}` hits `list(5)`.

**Then measured:** `TypeError: 'int' object is not iterable` — same for `3.5` and
`True`. The loop catches it (`loop.py:412`) and returns `{"error": "tool raised
TypeError"}`, so the turn survives. But that message names a Python type, not
anything the model can act on, and it costs a step.

**Why it is a defect and not a curiosity.** The function already decides that a
bare *string* where an array is specified is a formatting choice rather than a
contract violation, for the measured reason that models do it often enough to fail
turns over. A bare number is the same class of choice, given the opposite handling.

**Fixed** (`554623c`). Coerced, then answered with the honest "none of these
parsed as a supported indicator" and the value echoed back — the same answer a
mangled hash gets. Only `TypeError`, only around the coercion; any other exception
still degrades through the loop's guard as before.

**Proven to fail pre-fix** by restoring the unguarded `list(raw)`: exactly the 3
parametrized cases fail, the other 30 stay green.

## CHECKED AND CLEARED — 4 suspicions that did not survive execution

These are recorded because a non-finding that was actually checked is worth more
next session than a lead that gets re-chased.

**1. `autouse` changed 30 tests that never asked for it.** Sound. The only
`usage_counters` reference in `tests/test_chat_sse.py` is the fixture itself (the
"limited" at line 604 is email-subject text); **no test in the file asserts a limit
or a usage count**, so clearing after each one cannot mask a failure.
`test_hardening_surface.py`'s `clean_usage` resets **before and after**
(lines 87-91), so it inherits nothing. And the DELETE cannot race the app's own
claim: `ci.sh:23` runs `pytest -q` **serially** — no xdist. (Across *concurrent*
runs on one host it still could, but that is standing follow-up 8's shared-
workspace problem, not new.)

**2. The stale-read pin monkeypatches a shared object.** It does not.
`ActionExecutor.__init__` builds its own `ProposalSettlement(pool)`
(`settlement.py:387`), and the test constructs its own executor, so
`executor._settlement.get = _stale_read` cannot outlive the test.

**3. A provider failure could leak configuration into a tool result.** It cannot.
Every reason in `provider_failures` is a fixed literal — `BREAKER_OPEN_REASON`,
`INPUT_REJECTED_REASON`, `"timed out after Ns"`, `"unreachable or returned an
error"`, `"unexpected error"` (`fanout.py:30-31, 55-70`). The raw exception goes to
`logger.warning` only. This mattered because tool results enter the model's context
and the model writes the analyst's answer from them.

**4. Unbounded model strings reaching the extractor and OpenSearch.** The lead was
that `_resolve` calls `extract()` on model-controlled strings of any length and
`lookup_cve` forwards ids. Checked: the loop sends `max_tokens=2000`
(`PROBE_MAX_TOKENS`), so one call's entire argument blob is single-digit KB — not
the 32k the lead assumed. `lookup_ids` builds **`term` clauses**
(`kb/service.py:519`), not a query-string, so an operator-shaped id is a term that
matches nothing rather than syntax. `EnrichmentService.enrich` **does not persist**,
so a NUL never reaches Postgres (the S13 paste-boundary problem does not recur
here). The `MAX_TOOL_ARG_ITEMS` count cap remains the useful bound, and it is now
also applied to the observables those strings yield (FIXED 1).

## NOT A FINDING, BUT A DECISION OWED — the carry dict's key space

`OutputScanner._carries` is keyed by whatever string the caller passes, and the
S24 comment closes the space **by convention**: "call sites pass literals, never
model output." That is true today (four literals). D-031 adds a tool-results
channel, and a per-tool-call channel name would grow the dict without bound inside
a single turn.

No defect exists yet and none was manufactured. This is flagged where the wiring
will have to answer it: **the tool-results channel must be one literal, not one per
call.** If a future caller needs per-call granularity, the key space should be
closed in code rather than in a comment.
