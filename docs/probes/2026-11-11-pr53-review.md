## Must fix in #53

1. **A failed connector undo can never be retried** (`auspex/connectors/dispatch.py:77`, `auspex/actions/settlement.py:1100-1107`). A failed undo returns the row to where it was, so that it can be tried again. But the undo job's key is `connector.undo:proposal:<id>:undo` on every attempt. `enqueue` returns the existing job whatever its status (`auspex/jobs/queue.py:131-143`), and `_answer` sees it is `failed` and raises at once. **Reproduced:** the first undo fails because the SIEM has no recorded reopen. The second undo, with the SIEM answering, gets the same 500 back in about 70 ms, and there is still only one undo job (`failed`). The change can never be put back from the platform. The same happens after "the core stopped waiting before an Edge Agent claimed it", where nothing ran at all. **Direction (your call):** a job that ended without running, or that failed, should let a retry enqueue a fresh job. The handler's `ctx.idempotency_key` can stay the operation key, so the handler still drops a repeat. "Never a second run" only has to hold for a job that is done, or that may have run.
2. **The approval policy is not applied at D-048's Run door** (`auspex/routes/proposals.py:415`, `settlement.py:789`). `execute_stale_approval` lets any Analyst run an approved proposal that no run ever started, and the docstring itself calls that "a decision made now" (`settlement.py:808`). S34 makes such rows common: an approval made while the agent is offline stays `approved`. **Reproduced:** with `write` set to `[admin]`, an analyst's approve gets 403 ("needs the role admin; yours is analyst"). The same analyst then presses Run on the admin's stale approval and gets **200, executed**. **Fix:** apply the presser's policy (`policy.approvable`) to the stale run's claim, the way approve's claim does, with the policy's 403. Add a test for a barred analyst and one for barred provider staff.
3. **A grant can be written against a package nobody granted it for** (`auspex/integrations/store.py:266-290`). `set_grants` checks the action names against `current.content_hash`, read before its transaction, then writes without checking the hash again. If an admin changes the package between that check and the write, the new package gets grants that were checked against the old one, and your review #1 fix exists to stop that. **Reproduced** by forcing the package change in between: the integration pins the new package with `close_alert` granted. **Fix:** guard the UPDATE with `AND content_hash = <the checked hash>`, and refuse in words if it moved ("the integration's package changed; grant again"). Add a test.

## Smaller: fix or log, each your call (record which)

- **s1:** the core waits 60 s for execute and undo (`dispatch.py:33`), and the agent's timeout for them is also 60 s (`auspex/edge/agent.py:37`). The core's clock starts at enqueue, so a slow execute that succeeds is recorded as `incomplete` with unknown effects, and nothing reconciles it later. Previews and observes already have a margin (25 s against 30 s), and the comment there says why.
- **s2:** `bind()` now raises inside the handler's try (`sdk/auspex_sdk/invoke.py:143`), so the harness's `wrap` reports a caller's missing argument as `close_alert.dry_run: handler raised CommandError: close_alert: param 'alert_id' is required`, blaming the handler (reproduced). Before, it was just `close_alert: param 'alert_id' is required`. The existing test still passes because it matches a substring.
- **s3:** the edge API's `_check` (`auspex/edge_api/routes.py:176`) repeats `auspex_sdk.invoke.check`. TD-077 was about this kind of duplication.
- **s4:** a granted **read-risk** connector action is offered to the co-analyst (`auspex/connectors/resolve.py:66` offers every granted action, whatever its risk). Calling it runs the dry-run job on the agent, and then the INSERT is refused by `proposals.tool_level`'s CHECK (`auspex/migrations.py:110`, write or destructive only). The model is told "proposing raised CheckViolationError". I checked this in the code and did not run it. (The reviewer's version, a 500 on approving such a proposal, cannot happen, because the row is never written.) Either refuse to grant or offer read actions, or decide what a connector's read action means.
- **s5:** connector manifests are not checked for one action's role being another action's function, such as action A's undo being action B's execute. The core's registry refuses that for built-ins (`auspex/actions/registry.py:100-111`), but compiled connector actions never go through it. This was true before S34 and is outside TD-071's scope. A TD entry is enough.
