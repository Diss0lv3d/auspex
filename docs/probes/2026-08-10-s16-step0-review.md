## 1. DEFECT — the re-open event's `falsifies` link is lost silently, and forever

The lead as written in NEXT-SESSION.md was that `satisfy_documents` links the
S14 event by natural key including `change_kind`, so it only lands if
`RetroHuntSink` already wrote the match — true of the order
`IngestScheduler.from_settings` happens to construct `FanoutSink` in, and of
nothing else.

**Reproduced.** Same batch, same doc, only the two constructor arguments swapped:

```
[angle1 control ] FanoutSink(RetroHuntSink, WatcherSink)
                  falsified_claim='CVE-2026-79001 is not known to be exploited…'
[angle1 reversed] FanoutSink(WatcherSink, RetroHuntSink)
                  match_written=1  watcher_satisfied=['kev_listing']
                  falsified_claim=None          ← LINK LOST
```

Both sinks report success. Both logged their INFO line. The watcher is correctly
satisfied, the match is correctly written, and the sentence telling the analyst
*which claim the intel contradicted* is simply gone.

### Two things the review found that the lead did not say

**(a) The loss is PERMANENT.** The satisfy UPDATE is guarded on
`status = 'open'`, so once the watcher is satisfied no later cycle ever revisits
it — including a later, correctly-ordered delivery of the same change:

```
[angle1 permanence] after reversed          = None
[angle1 permanence] after correct re-emit   = None      ← PERMANENT = True
```

**(b) Order is not the only trigger — and this is what decided the fix.** The
retro-hunt sink is *designed* to swallow its own failures so ingest outlives
them. So the watcher can legitimately be satisfied in a cycle that recorded no
match at all. Correct order, healthy next cycle, link still gone:

```
[angle1b] after failed sweep : matches=0  satisfied=['kev_listing']
[angle1b] after healthy cycle: matches=1  falsified_claim=None
          → LINK LOST DESPITE CORRECT ORDER = True
```

That rules out "enforce the sink order" as a fix: ordering was one way in, not
the cause. The cause is that the link was WRITTEN once, from one side, at a
moment when both rows were not guaranteed to exist.

This is the third instance of the same class in two sessions — S15 fixed the
verdict trail's head being decided by transaction start rather than write order,
and the `auspex.watchers` ↔ `auspex.enrich` cycle that resolved only under a
lucky import order. Correct by order, not by construction.

### The fix — derive the link instead of writing it

`satisfy_documents` no longer reaches into `retrohunt_matches`. It records
`watchers.satisfied_change_kind` — which change contradicted this claim — and
stops. `list_matches` derives the pairing at read time:
same workspace, same observable, `satisfied_by = m.doc_id`,
`satisfied_change_kind = m.change_kind`.

Neither writer has to run first, or at all, for the analyst to see the claim.
All four loss modes above now resolve:

```
[angle1  reversed order      ] LINK LOST = False
[angle1  permanence          ] PERMANENT = False
[angle1b sweep failed a cycle] LINK LOST DESPITE CORRECT ORDER = False
```

`retrohunt_matches.watcher_id` is dropped, with its existing links backfilled
into the new column first, in one idempotent guarded statement
(`auspex/migrations.py`). One source of truth, not two.

**Ordering made explicit rather than left to the planner.** The pairing is not
unique over time: a later verdict registers its own watcher of the same kind and
a re-emitted change satisfies that one too, leaving two satisfied rows with
identical keys. The LATERAL takes the newest by `satisfied_at` — which is what
the old column did when the second satisfaction overwrote it, except now it is a
decision instead of a write-order accident. Pinned by
`test_two_verdicts_satisfied_by_one_doc_resolve_to_the_newest_claim`.

### The plan is probed, not argued

25,000 satisfied watchers + 25,000 matches, VACUUM ANALYZEd (STATE.md host
note). The satisfied population is the one that grows **without bound** — a
satisfied watcher is never revisited and never deleted — so this is the read that
had to not degrade. New PARTIAL index `idx_watchers_satisfied_obs`
(`status='satisfied'`), mirroring S15's `idx_watchers_open_obs_kind` at the other
end of a watcher's life:

```
Limit (actual time=0.235..0.339 rows=50 loops=1)
  -> Nested Loop Left Join (actual rows=51)
       -> Index Scan using idx_retrohunt_matches_ws_status on retrohunt_matches m
       -> Index Scan using observables_pkey on observables o  (loops=51)
       -> Limit -> Index Scan using idx_watchers_satisfied_obs on watchers (loops=51)
            Index Cond: ((observable_id = m.observable_id) AND (satisfied_by = m.doc_id))
            Filter: ((workspace_id = m.workspace_id) AND (satisfied_change_kind = m.change_kind))
Execution Time: 0.373 ms
```

The outer LIMIT is applied before the LATERAL, so the derivation runs once per
event on screen (51 loops for a 50-row page), never once per satisfied watcher.
Asserted by `test_deriving_the_claim_plans_on_the_satisfied_index`.

## 2. CONFIRMED GAP — a dead falsification checker is indistinguishable from an idle one

`FanoutSink` catches per sink and both sinks already catch internally. Nothing
counts consecutive failures.

**Reproduced.** 50 consecutive cycles with the watcher check failing every time:

```
[angle2] open watchers still open  = ['kev_listing', 'provider_escalation', 'record_withdrawn']
[angle2] re-open events written    = 1
[angle2] falsified_claim           = None
         → indistinguishable from 'nothing to do': same rows, same API output
```

Fifty stack traces in the log, and every analyst-facing surface reads exactly as
it would if the platform had checked diligently and found nothing. `GET
/api/watchers?status=open` returns three standing claims either way.

This is not merely a monitoring gap — it is an honesty gap of the same family the
whole feature exists to close. "No claim of yours has been contradicted" is an
**absence claim**, and an absence claim from a checker that stopped running is
false.

**Deliberately not fixed in Step 0.** S16's deliverable is precisely the view
that makes absence claims at scale ("what changed while you were away, what is
now stale, what contradicted us"). The fix belongs at that surface, where the
claim is actually made, rather than as a counter nobody reads. Precedent for the
shape: `auspex/enrich/breaker.py` (consecutive-failure threshold). Carried into
the S16 goal below, not into TECHNICAL_DEBT.md.

## 3. SOUND — escalation satisfaction under concurrent enrichment

S15 pinned concurrent REGISTRATION but never concurrent `check_escalation`. Two
`persist_enrichment` calls raced on ONE observable via `asyncio.gather`, one
escalating (`suspicious → malicious`) and one not (`→ suspicious`):

```
[angle3] trail = ['suspicious', 'malicious', 'suspicious']
[angle3] flips = [('suspicious','malicious'), ('malicious','suspicious')]
[angle3] watcher rows after the race:
   kev_listing          superseded
   record_withdrawn     superseded
   provider_escalation  satisfied    satisfied_by=flip:d4fc672b-…
   record_withdrawn     superseded          ← the malicious verdict's only claim
   kev_listing          open
   record_withdrawn     open
   provider_escalation  open
[angle3] OPEN watchers left = 3, owned entirely by the newest verdict
```

No interleaving, no duplicate open set, no lost satisfaction. The reason is
already documented at `auspex/enrich/store.py:46` and holds here too: the
`observables` upsert's `DO UPDATE` takes a row lock held to commit, so two
enrichments of the same observable are serialized from that point through
`check_escalation` and `register`. The escalation that happened is recorded with
its flip id; the de-escalation that followed correctly re-registers the claim.
**No fix needed** — recorded as sound so S17 does not re-litigate it.

## 4. SOUND — `claim` text is bounded in practice

`claim` is `text` and unbounded in the schema, built from `observable.value` plus
provider names.

- The S4 classifier's `_CVE_RE` is `\bCVE-\d{4}-\d{4,7}\b`
  (`auspex/classify/observables.py:107`), so a CVE value is at most 16 chars.
- Provider names come from our own provider registry, not from customer input.
- Measured worst case at 12 providers: **197 chars** (`provider_escalation`, the
  only kind that interpolates a list). `kev_listing` 98, `record_withdrawn` 64.
- Non-CVE observable (sha256) → `['provider_escalation']` only, same bound.
- Zero signals → `synthesize` returns `None`, so no verdict and no watchers at
  all. There is no "no sources answered" claim to construct.

**No fix needed.** Recorded because "probably fine" was the S15 assumption and
this is the execution that makes it a fact.
