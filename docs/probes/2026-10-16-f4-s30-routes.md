## What F4 codes against

1. **`GET /api/auth/me`** returns `user` {id, email, display_name},
   `organization` (the HOME one: id, name, kind), `workspace` (the ACTIVE one:
   id, name, region, role, **`organization` as a bare name string**), and
   `workspaces[]` (id, name, region, role, `via`, **`organization` as an
   object** {id, name, kind}), home organization first, then by name.
   - The two `organization` shapes differ. The page reads the active
     workspace's organization **kind** from the matching `workspaces[]` entry.
2. **Who sees what in the switchable set** (the page never computes it):
   | Person | `workspaces[]` |
   |---|---|
   | provider admin (no grant) | mssp only |
   | MSSP analyst, explicit | mssp (analyst), bank (analyst, membership), **gov (viewer, membership — an explicit membership reaches a restricted client)** |
   | MSSP analyst, provider-wide | mssp (analyst), bank and telco (analyst, `via: provider_wide`) — **not gov** (restricted) |
   | client admin / analyst / viewer | bank only, as admin / analyst / viewer |
   - A provider-wide grant carries the provider membership's role into each
     client.
3. **`POST /api/auth/switch {workspace_id}`** → 200
   `{access_token, token_type, workspace: {id, name, role, region}}`.
   **The answer names no organization**: the page re-reads `/me` with the new
   token to show the active client.
   - The new token's `/me` is active in the target; **the old token stays
     valid for its own workspace** (checked after every switch). The page must
     replace the tab's token, not add one.
   - Refusals: the restricted client (provider-wide only), a missing workspace,
     the client admin's own provider, the client analyst's restricted sibling →
     **404 `{"detail": "Unknown workspace"}`**, the same answer for all.
   - A malformed id → **422 with `detail` as an ARRAY** (pydantic's list of
     error objects, echoing the input). The shared error copy must handle a
     non-string `detail`, and never show the echoed input as markup.
   - An API key → 403 "Switching requires a login session" (`/me` itself
     answers 200 to the key).
4. **Roles at the server** (the page only reflects them):
   - a **viewer's `POST /api/chat` is 403** "This needs the analyst or admin
     role in this workspace." — **even a question the shortcut would answer**
     (the role dependency runs before the route body). The composer is a door
     a viewer cannot use.
   - a viewer's proposal door (`reject`) is the same 403; a viewer's
     `GET /api/proposals` is 200.
   - an analyst's `GET /api/workspace/members` is 403 "This needs the admin
     role in this workspace."; the client admin's is 200 (4 members).
5. **Residency**: in the ksa client, a deep turn is
   **403 `application/json`** before any stream starts:
   "This workspace's data must stay in region ksa, and the platform's engine
   here processes in region global, so it cannot run this request. Answers that
   need no engine still work." No chat session was stored (`0`).
6. **A removed membership**, at the next request:
   - `GET /api/auth/me` → 403 "You no longer have access to this workspace."
     So does every other route on that token. **`/me` cannot list where else
     the person may go on a dead token**; the page can only sign them in again.
   - the open approvals stream (opened before the removal) sent
     `data: {"error": "You no longer have access to this workspace."}` and
     ended.
   - a dev login for a person left with no workspace → 403 "There is no
     workspace you may enter. Ask an administrator to add you."
