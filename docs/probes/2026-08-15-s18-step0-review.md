## 1a. The strongest lead, refuted: half-life fan-out costs almost nothing

The suspicion was structural and looked right: `bounds` is `edges × half-lives`,
so each extra distinct `half_life_days` adds three more LATERAL descents, and the
S17 measurement ran on a workspace with exactly **three** families.

Seeded 25 000 verdicts per workspace, varying only the number of distinct
half-lives, 7-day window, median of 5 runs:

| distinct half-lives | LATERAL descents | new query | old (pre-`e57ab0c`) | seq scan? |
|---|---|---|---|---|
| 3 | 9 | 1.9 ms | 25.2 ms | no |
| 20 | 60 | 2.5 ms | — | no |
| 50 | 150 | 3.6 ms | 15.9 ms | no |
| 200 | 600 | 3.8 ms | 24.0 ms | no |
| 500 | 1 500 | 4.9 ms | 16.9 ms | no |
| 2 000 | 6 000 | 12.2 ms | 16.1 ms | no |

At **2000 families and 6000 index descents it is still faster than the query it
replaced**, and it never once fell back to a scan. The recursive loose-index-scan
that enumerates the families is itself trivial: 51 rows in 0.196 ms at 50
families, each step one index-only descent of ~3 µs.

The reason it does not blow up is the part worth remembering: **the same rows are
partitioned into more families**, so each descent finds proportionally fewer of
them. Total work tracks the rows that actually crossed a band, not the number of
descents. The multiplicative term is real and the thing it multiplies is tiny.

Pinned by `test_the_decay_read_stays_index_driven_with_many_half_life_families`
(50 families, 25k rows) — not because the cost is at risk, but because the SHAPE
is: if a planner change ever abandons the per-family descent, that asserts.

## 1b. The regression S17 logged but never bounded — and it is worse than 9%

S17 recorded "at the widest legal window (365 days) the new shape is ~9% SLOWER"
and left it there. Bounded now. Old vs new, median of 3–5 runs:

**25k verdicts, 3 families** (S17's own shape):

| window | new | old | ratio |
|---|---|---|---|
| 7 d | 2.1 ms | 25.2 ms | 0.08 |
| 90 d | 9.6 ms | 24.9 ms | 0.39 |
| 180 d | 16.5 ms | 25.5 ms | 0.65 |
| 365 d | 30.7 ms | 26.1 ms | **1.17** |

**100k verdicts, 12 families** (the size the original 143 ms defect lived at):

| window | new | old | ratio |
|---|---|---|---|
| 7 d | 5.4 ms | 150.9 ms | 0.04 |
| 30 d | 13.8 ms | 156.7 ms | 0.09 |
| 90 d | 37.0 ms | 143.1 ms | 0.26 |
| 180 d | 67.7 ms | 146.3 ms | 0.46 |
| 270 d | 104.4 ms | 136.5 ms | 0.77 |
| 365 d | **161.4 ms** | 133.8 ms | **1.21** |

**The crossover is ~300 days at 100k/12 families and ~185 days at 25k/50
families** — it moves in with more families, because more families means wider
total coverage per window. The regression at the maximum is 17–39%, not 9%.

The number that matters: **161 ms at `days=365`, which is slower than the 143 ms
defect the rewrite existed to fix**, and `days` is a user-supplied query
parameter (`le=MAX_SINCE_DAYS`, `auspex/routes/timeline.py:240`) — any analyst can
ask for it.

Why it loses at wide windows: the bounds ranges approach the whole history, so
nearly every verdict becomes a candidate, and **every** candidate then pays one
index descent for "is this still the current verdict?" — 30k+ probes to return 50
rows.

### A costed fix exists and is deliberately NOT taken this session

The ordering key (half-lives elapsed) is computable from a candidate row alone,
so the candidates can be sorted BEFORE the current-check and the `LIMIT` allowed
to stop it early. Measured at 110k verdicts, output compared row-for-row:

| window | current | variant | speedup |
|---|---|---|---|
| 7 d | 7.9 ms | 2.8 ms | 2.80× |
| 90 d | 51.2 ms | 17.4 ms | 2.94× |
| 365 d | 135.4 ms | 56.5 ms | 2.40× |

Identical output at every window and at limits 50 / 200 / 1000. The plan confirms
the mechanism: `loops=59` on the current-check instead of ~30 000. It beats the
OLD query at every window too, so it removes the crossover entirely.

**It is not shipped, and the reason is the same class of problem as lead 2.** The
early stop depends on the candidate ordering surviving into the outer query,
which Postgres does not guarantee — a non-recursive CTE referenced once may be
inlined and its `ORDER BY` discarded. That makes it a second load-bearing
invisible construct, and a worse one than `OFFSET 0`: removing the fence makes
the query SLOW, while losing this ordering makes the digest render **the wrong
rows first** while still returning the right set. A silent correctness failure is
not an acceptable trade for 2.4× on the rarest window, decided mid-review.

**`MAX_SINCE_DAYS` stays at 365.** 161 ms for an explicit whole-year request is
acceptable next to 5–14 ms for the 7–30 day windows an analyst actually opens;
narrowing the API to protect a tail that costs 161 ms would be the wrong trade.
Logged as TD-024 with these numbers so the next session inherits a costed
decision rather than a worry.

| | time | plan |

## 3. The four-clause `trustworthy` rule holds (verified non-finding)

Matrix executed against `Digest.trustworthy`:

| roster | trustworthy |
|---|---|
| empty (no scheduler) | False |
| healthy `ingest-cycle` only | True |
| crash loop: failing, never succeeded | False |
| 2 failures but a past success | True |
| degraded (≥3 consecutive) | False |
| healthy cycle + **degraded consumer** | **False** — not masked |
| healthy cycle + consumer failing under threshold | True (intended tolerance) |
| ingest disabled, cycle never ran | False |
| only never-run checkers | False |

The three named questions answered: a healthy cycle counter does **not** mask a
degraded consumer (clause 2 is `any`, evaluated before the cycle can vouch); a
workspace with ingest disabled reports a roster of never-run counters, not an
empty one, and clause 4 refuses it; clause 3 is **not** too eager — a first-cycle
transient makes the digest untrustworthy and one success heals it immediately,
with no stickiness.

One case is worth naming because it looks like a hole and is not: a consumer at
0 failures / 0 successes IS vouched for by a healthy `ingest-cycle`. That is the
designed behaviour — every `emit()` is guarded on a non-empty doc list, so in a
quiet week a live consumer and a dead one are the same shape, which is exactly
why the cycle counter was added. Distinguishing them needs a durable heartbeat:
already logged as **TD-022**.

## 4. Three defects in the contract's own rails (not on the list)

Every refusal in `validate_spec` is a claim that something cannot be built, so
each was attacked. The eight documented rails all held, including the
`object.__setattr__` forge reaching `planner_description` and the registry. Three
things got through.

### 4a. The undo slot was guarded by exactly one rule

`undo.handler is spec.execute` was the only check. Everything else was legal:

| declared | registered? | what running the undo actually did |
|---|---|---|
| undo = this action's own `dry_run` | **yes** | previewed. Restored nothing. |
| undo = another action's `dry_run` | **yes** | ran `delete_file:dry`. Restored nothing. |
| undo = another action's `execute` | **yes** | ran `delete_file:EXECUTE` — undoing an isolation **deleted a file** |

All three reported `reversible=True` and put `Undo: …` in the planner text and
in front of an approver. This is the failure `UndoSpec`'s own docstring calls
worse than having no undo at all — the approval was granted on its strength —
and it is the same family as the `dry_run=another_action` case S17 caught by
running the contract. `validate_spec` can only ever see one spec, so the
in-spec case is fixed there and the cross-spec cases in the registry, in both
registration orders.

Fixed: `auspex/actions/types.py` (own `dry_run`), `auspex/actions/registry.py`
(`_undos` book-keeping, both directions). Four regressions.

**One existing test was encoding the hazard**: `test_two_actions_may_share_a_dry_run`
used the first action's undo handler as the second action's `execute`, so
"undoing" the isolation would have closed a ticket. Its stated point (sharing a
preview is legitimate) is preserved with a distinct callable.

### 4b. Parameter names were unvalidated wire identifiers

The action NAME is checked because "it is a tool name on the wire". A parameter
name is a JSON-schema property key on the SAME wire and was checked by nothing.
All of these reached `wire_spec` and landed in both `properties` and `required`:

    ''   '   '   'host id'   'host-id'   'π'

An action with a parameter named `''` can be approved and is then uncallable — no
model reliably emits it — and S2's harness already measured that models mangle
unusual identifiers. While fixing it: the action-name rule itself was
`name.replace("_", "").isalnum()`, which is **true for `π`** and every other
unicode letter, so it read as ASCII-only and was not. Both now use one explicit
`[A-Za-z_][A-Za-z0-9_]*`.

### 4c. An action could silently shadow a tool the loop dispatches

`ActionRegistry` and `ToolRegistry` never consult each other, and the model sees
one namespace. Executed:

- action `isolate_host` — risk **destructive**, planner text "requires human
  approval before it runs"
- tool `isolate_host` — level **read**
- the model is told the action's description, emits that name
- `AgentLoop._dispatch` resolves names in the **ToolRegistry** → runs the tool
- the D-014 gate reads the **TOOL's** level → **auto-executes, no approval**

The action's declared risk is bypassed by a naming coincidence, and the gate
never sees it. Latent in S17 because nothing dispatched actions; **S18 is the
session that changes that**, which is why it is fixed now rather than logged.

Fixed in `auspex/agent/loop.py`: `_refuse_shadowed_actions` raises at loop
construction — the moment the two namespaces meet, before a token is sent, and
independent of the order the registries were filled. Raising rather than
renaming or preferring one: silently picking a winner leaves the model told
about an action that is not the thing it can call.
