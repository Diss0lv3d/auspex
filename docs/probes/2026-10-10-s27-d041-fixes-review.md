## Cleared — checked by execution, nothing found

- **`cd44b4f`, one status-CHECK block.** It is the only statement that defines
  `proposals_status_check` (`auspex/migrations.py`). The one other CHECK on the
  table is `abandoned_from`'s, which lives on an `ADD COLUMN IF NOT EXISTS`
  and so is never re-validated after the first boot.
  `test_startup_survives_every_status_a_proposal_can_be_in` is green, and the
  app booted through `./ci.sh`'s container build and two rebuilds today.
- **`a3cf81d`, claim tokens.** Traced every claim and every finish:
  - Every claim (`execute`, `undo`) mints `claim_token`, and every exit clears it.
  - `abandon` copies the token to `abandoned_token`.
  - A late answer lands only on `abandoned_token`, and only into an empty column.
  - Legacy wedged rows, claimed before the column existed, carry a NULL token.
    They can still be abandoned. Their late answer (`= NULL`) never matches,
    which is correct: that handler died with the old process.
  - One contrived corner is recorded rather than fixed:
    1. undo T1 is abandoned;
    2. a fresh undo T2 starts;
    3. T1's late answer fills the empty `undo_result`;
    4. T2 is abandoned too.

    T2's own late answer is then dropped, because the column is no longer
    empty, so the row shows T1's answer under T2's abandonment. It needs two
    stale claims on one row, and every executable action today is a single
    local statement.
- **`60eb36c`, observe rails.** `type(found) is not int` refuses `None`, `bool`
  and negative counts, and the `ActionSpec` validation keeps `observe` distinct
  from the run, the dry run and the put-back. Existing tests cover each.
- **`cee69e4`, legacy failed rows.** A `failed` row with no `effects` is
  undoable. Can a NEW-path `failed` row end up without `effects`? Checked:
  `failed` is only ever written from `execute`'s except-path, and that path
  always writes `effects`. The late-write fills only an empty `result`.
- **`4679da6`, twin index.** It is used, and it files a 20 000-char note.
  **One bound, stated rather than fixed.** jsonb `=` and md5-of-text disagree
  on numbers that differ only in scale. Probed on the dev Postgres:
  `'{"n":1.0}'::jsonb = '{"n":1}'::jsonb` is **true**, and their md5s
  **differ**. So the index's md5 pre-filter misses twins that the exact jsonb
  equality would have named. This is reachable: action arguments are filed
  as the model's raw JSON, with no normalisation by `ParamType`
  (`auspex/agent/loop.py`, `_propose_action`). No builtin action takes a
  number today. Recorded in the index's migration comment. It matters the day
  an action declares an INTEGER or NUMBER parameter.

## Found, not part of these fixes — logged as TD-042

The review found a gap from S18 that sits next to TD-028a: **an `approved` row
whose run was never claimed has no door out and no place in the queue.**

- `docs/probes/s27-review/probe_approved_wedge.py` approves a proposal and then
  stops before execute's claim, which is what a process death between the
  two statements leaves behind.
- Result: `in queue: False`; `reject`, `abandon` and `keep` each return
  `already_decided`; the status stays `approved`.
- The same state is the honest end of an execute-time refusal (spec changed,
  risk changed), which the route already reports.
- The crash case has no surface at all. Logged rather than fixed: a door here
  (re-run, or withdraw) is a decision about what an approval means once time
  has passed. See TECHNICAL_DEBT.md TD-042.
