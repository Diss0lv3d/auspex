# 2026-10-16 — S31: a sign-in racing a rehome stamps the new home on the old home's trail (B-025)

Found by S31's fresh adversarial review of the B-021 fix (`b1fa61e`). The race is

## The code, as it stands (`auspex/tenancy/entry.py:15-29`, at `3d5007b`)

`enter()` decides access first (`landing` or `enterable_workspaces`), then reads
the person's home organization in a separate query (`home_org`), then records
`workspace.enter` in the entered workspace with `actor.organization` set to that
home. The two reads are not in one statement or one transaction.

## Reproduction (deterministic, forced order)

`docs/probes/s31-b025/race_enter.py` builds a provider, its client `client1`
with a workspace, an unrelated direct organization `othercustomer`, and a person
homed in `client1` with an analyst membership there (all under the prefix
`t-s31-b021rev`). It wraps `entry.home_org` so that, after `landing()` has
chosen `client1`, the membership is deleted and the CLI's `rehome_person` moves
the person to `othercustomer`; then the real `home_org` runs.

Run from `.venv` on the host against the dev Postgres, 2026-10-16:

```
entered: t-s31-b021rev-client1
client1's trail, newest: workspace.enter actor.organization = t-s31-b021rev-othercustomer
cleanup, orgs left: 0
```

`client1`'s admins read their trail through `GET /api/audit`, so they would read
`othercustomer`'s name: another customer's.

## Bounds

- The window is between two queries of one sign-in or switch (milliseconds); it
  needs a workspace admin to remove the membership and the operator to run
  `rehome-person` inside it.
- The script forces the order with a wrapper; it was not hit by timing.
- It cleaned up every row it made (`orgs left: 0`).
