## Root cause

- **In turn 1 the model passed the short id**, `ipv4-9bf483a1`, which it had
  read in `enrich_observable`'s result.
- **In a fresh chat it has never been shown that id**, so it passes the
  indicator as the analyst wrote it.
- **The action resolves only the id:** `_resolve` matches `obs_id = $2`
  (`auspex/actions/builtin.py:46-64`). So the dry run says "Nothing: no
  observable '185.220.101.52' in this workspace", the proposer declines
  (D-045), and the model reports that the indicator does not exist.
- **The read tool already accepts both forms.** `enrich_observable` tries
  the id first, then parses the string with the route's own extractor
  (`auspex/agent/capabilities.py:140-185`). The note action does not, and the
  short id is a pure function of the type and value (`observable_id`,
  `auspex/migrations.py:122`).

Turn 1 also wrote its answer twice. That is TD-036, already recorded, and not
this bug.

## The fix (`29209fa`, Burhan's call: code, accept both forms), live

**The change.** `_resolve` tries the short id first. If that finds nothing,
it parses the string with the route's own extractor and looks up exactly one
indicator's id, inside the workspace. A string that names two indicators
targets neither. The parameter description now reads "The observable's short
id, or the indicator itself". That changes the action's declared fingerprint,
so a note approved before the deploy and not yet run must be re-proposed; the
dev DB had none.

**Tests.** `./ci.sh` green at 1375 tests. Three tests failed before the fix
and pass now, and two guards (tenancy, two indicators) pass either way. Three
mutants, 3 caught: an id-only lookup, the first of several indicators, and a
lookup not scoped to the workspace.
