## Angle 1 — tenancy of the cross-workspace sweep — **SOUND**

The sweep deliberately does not filter by workspace (`idx_observables_type_value`
leads with `type`, and ingest is platform-global). The question was whether
anything downstream leaks: two workspaces settled the SAME CVE with different
labels, then A re-enriched into a flip.

```
sweep hits across workspaces: 2 (expect 2)
   ws=A label=suspicious
   ws=B label=benign
matches written: 2
match rows whose observable/verdict belong to ANOTHER workspace: 0
open_match_for(ws=A, observable=B's row): None   (expect None)
open_match_for(ws=A, observable=A's row): found
flip in ws=A: suspicious->malicious trigger=retrohunt:CVE-2026-90001 match_belongs_to=A
flips linking ANOTHER workspace's match: 0   (expect 0)
```

The named attack — "can a flip in workspace A link a match belonging to
workspace B?" — cannot happen: `open_match_for` filters on `workspace_id` AND
`observable_id`, and `observables.id` is already workspace-unique, so the pair
is doubly scoped. Each hit carries its own `workspace_id` into the row it
writes, and the LATERAL that reads the verdict is scoped to `o.workspace_id`.
No change.

## Angle 2 — flip-writer contention — **one CONFIRMED defect, one sound**

### 2a/2b. The race that was suspected: **sound**

`latest_verdict` reads the trail and the verdict insert follows with no
`FOR UPDATE` between — the shape the S13 review found broken in `add_evidence`.
Ten rounds of `asyncio.gather`, two enrichments changing the same observable's
label:

```
runs with a duplicated/lost flip: 0/10   (expect 0 if serialized)
```

It holds, but not for the reason the code says anywhere: the `observables`
upsert (`ON CONFLICT DO UPDATE`) takes that row's lock and holds it to commit,
so the two transactions are already serialized before `latest_verdict` runs. The
flip writer depends on a lock taken in a different module and no comment said
so. Now named on both sides (`enrich/store.py`, `retrohunt/flips.py`) and pinned
by `test_concurrent_enrichments_of_one_observable_record_exactly_one_flip`.

### 2c. The defect the angle actually exposed: **CONFIRMED — trail order**

```
verdicts.created_at DEFAULT = now()
now() moves inside a transaction? False   (False ⇒ transaction_timestamp)
clock_timestamp() - now() after 250ms sleep: 0.253s
```

`now()` is `transaction_timestamp()` — fixed at a transaction's FIRST statement.
`verdicts.created_at` is not a display field: `latest_verdict` and the sweep's
LATERAL both define **the current verdict** as the newest row by that column.

The interleaving, executed. Transaction B begins and upserts an unrelated
observable — exactly what `persist_enrichment` does whenever a turn carries more
than one, since it sorts by `(type, value)` before writing — fixing B's `now()`.
B then blocks on the shared observable's row lock while transaction A, which
began LATER, writes a verdict and commits. B proceeds and writes the newest
belief carrying the OLDER stamp:

```
verdict trail by created_at: ['benign', 'suspicious', 'malicious']
   last WRITTEN belief was 'suspicious' (transaction B, committed last)
latest_verdict() says: malicious
sweep's verdict_label_at_match: ['malicious']
flip trail: [('malicious', 'suspicious'), ('benign', 'malicious')]  (was 0 before)
   >>> latest_verdict disagrees with the last committed belief
```

Three consequences, all of them things this feature exists to state correctly:
the trail's head is a superseded label; the re-open event publishes that stale
label as `verdict_label_at_match`, which is the entire point of the event; and
the next enrichment computes `from_label` from a verdict that is no longer the
latest, so a flip is fabricated or missed. The flip list also reads in an order
its own verdict trail contradicts.

**Fix:** `clock_timestamp()` on `verdicts`, `retrohunt_matches` and
`verdict_flips` — read at INSERT time, which is the order the observables row
lock already serializes these writes into (B cannot reach its verdict insert
until A has committed, so B's stamp is strictly greater). Existing rows keep
their stamps; true write order is not reconstructible after the fact.
`retrohunt_matches` had the same bug in a second form — `record_matches` writes
a whole sweep in ONE transaction, so under `now()` every match in a batch tied
and `open_match_for`'s "newest open match" picked arbitrarily among them.

Regression: `test_the_trail_orders_by_write_time_not_by_transaction_start`,
verified to FAIL against the pre-fix default before being kept.

## Angle 3 — first-run KEV sweep cost inside `run_cycle` — **SOUND, measured**

The S14 review named the worst case: a KEV first-run refresh emits ~1,600 ids in
one batch (`scheduler.py:436`), which is 32 sequential swept chunks plus 32
`record_matches` transactions, all inside `run_cycle`. Measured with every one
of those 1,600 ids matching a held, settled observable — the pathological case
where every id is a hit:

```
observables in this DB right now: 24
sweep 1600 ids, 24 observables, 0 matches: 7 ms (32 queries)

seeding 1600 matching observables + verdicts ...
sweep  1600 ids -> 1600 hits: 16 ms
record_matches   -> 1600 rows : 159 ms
TOTAL inside run_cycle: 175 ms
re-emit (idempotent) -> 0 rows: 96 ms
```

175 ms, against a cycle that paces NVD single fetches at seconds apiece. It does
not belong off the critical path; the TD-008 precedent does not apply. TD-019's
"scheduler timing unobserved" bullet is narrowed to the part still true — the
cycle path has not been driven end-to-end — with the cost half closed.

## Angle 4 — `change_kind: "deleted"` as a re-open reason — **CONFIRMED (honesty)**

Both emitters mean one thing: NVD **rejected** a CVE we hold — `scheduler.py:383`
on the delta stream, `scheduler.py:451` on the KEV single-fetch path. There is
no "de-listed from KEV" kind; `deleted` is always a withdrawal.

S14 rendered it with the sentence written for a KEV addition:

> "New intel touches an observable this workspace already saw. This is a reason
> to re-examine, not a re-classification: no verdict has been changed."

That describes the opposite motion. Nothing new was learned about the
observable; the KB record a verdict may have rested on was **removed**. The
sentence points an analyst at evidence that no longer exists, in the one place
the platform is explaining itself.

**Decision: it stays in `TRIGGER_KINDS`.** A verdict whose cited source has been
withdrawn is a genuine reason to look again — arguably a stronger one than an
addition, because the ground moved rather than the picture. Only the claim was
wrong, not the trigger. Copy moved into `MATCH_NOTES` beside `TRIGGER_KINDS`,
keyed by kind, with a structural test asserting the two sets match so a kind
added later cannot inherit a sentence written for a different event — which is
exactly how this happened.

## Also re-measured: the SWEEP_CHUNK comment overclaimed

S14's comment said "at 50 the sweep is index-driven at every scale". Measured
across table sizes (VACUUM ANALYZE between, per the STATE.md host note):

```
observables(cve) = 1600
   batch   50: SEQ SCAN exec 0.365 ms
   batch  100: SEQ SCAN exec 0.368 ms
   batch  500: SEQ SCAN exec 0.774 ms
   batch 1000: SEQ SCAN exec 1.289 ms

observables(cve) = 25000
   batch   50: index    exec 0.288 ms
   batch  100: SEQ SCAN exec 3.391 ms
   batch  500: SEQ SCAN exec 4.592 ms
   batch 1000: SEQ SCAN exec 4.936 ms
```

At 1,600 rows the planner scans at every batch size and is right to — the table
is 22 pages and the scan costs 0.37 ms. The claim was false at the low end and
harmless there. The load-bearing part holds and is confirmed at 25k: batch 50
stays on the index where batch 100 does not, and the crossover rises with the
table, so a chunk that holds at 20k holds at every size above it. The comment
now states that instead of the stronger thing it can't support — S14's own note
that "a comment crediting the wrong cause is worse than none" applies to a
comment crediting the wrong guarantee.
