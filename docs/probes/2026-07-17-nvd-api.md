# Probe: NVD CVE API 2.0 — seed-corpus fetch (S6)

- **Date:** 2026-07-17
- **Target:** `https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=<id>`
  (keyless; public rate limit ~5 req/30 s — requests spaced 7 s)
- **Why:** S6 seeds the KB with a handful of real CVE records; S7's live NVD
  feed will consume this same shape. Fixture source of truth for both.

## Measured

5/5 HTTP 200, 0.8–1.7 s each, 4.7–87 KB bodies:
CVE-2021-44228, CVE-2024-3400, CVE-2017-0144, CVE-2023-23397, CVE-2019-19781.

## Response shape (fields we consume)

```
vulnerabilities[0].cve:
  id                "CVE-2021-44228"
  published         "2021-12-10T10:15:09.143"
  vulnStatus        "Analyzed"
  descriptions[]    [{lang: "en", value: "..."}, ...]   ← pick lang=en
  metrics.cvssMetricV31[0].cvssData.baseScore / .baseSeverity
    (fallback order: cvssMetricV31 → cvssMetricV30 → cvssMetricV2;
     V2 keeps baseSeverity on the METRIC, not inside cvssData)
  references[]      [{url, source, tags?}, ...]
```

## Quirks caught

- **CVE-2023-23397's en description is 54 chars** ("Microsoft Outlook
  Elevation of Privilege Vulnerability."). MSRC-sourced records can be terse
  — rendering must not assume a paragraph exists.
- Description lengths vary 54–713 chars in this sample; Log4Shell's body is
  87 KB mostly from `configurations` (CPE matrix) — trim fixtures to the
  consumed fields only.
- CVSS severity casing is UPPER ("CRITICAL").

## What our code must therefore do

- Parse via a single `nvd_to_doc()` (S6 seed + S7 feed share it), tolerant of
  missing metrics and terse descriptions.
- Fixtures: `auspex/kb/seed_data/nvd_cves.json` — trimmed to consumed fields,
  values verbatim from the live responses above.
