## Why the follow-up had no tools (answers the B1 prompt)

- **The classifier sees "dig deeper" as deep** (`classify` → `deep`, no
  observables).
- **The mode resolver reads only the current message.** "dig deeper" has no
  security vocabulary, so it resolves to `general`
  (`auspex/modes/resolver.py:129`). The session's indicator never reaches it.
- **The path is D-037, as ratified.** A dev-switcher endpoint carries no
  agent mode (`auspex/routes/chat.py:287-288`), so it stays conversational. A
  customer endpoint that is `prompted_tools`, `plan_only` or unprobed does the
  same, so this is not a dev-only path.
- **What the model is told:** the system prompt, the fence directive, turn 1
  (the IOC echo, fenced, saying "no signal from 5 connected sources — unknown
  to them"), "dig deeper", and the general directive. "Unknown to 5 sources"
  WAS in context. Nothing says what the platform cannot see. There is no
  WHOIS, RDAP, reverse-DNS or geolocation source, and nothing claims one.

## Root cause

**The platform had the owner and threw it away.** On turn 1 the IOC check
called AbuseIPDB and OTX, and both named the network
(raw-owner-fields.log):

- AbuseIPDB: isp `Google LLC`, domain `google.com`, usage
  `Data Center/Web Hosting/Transit`, `US`, hostname
  `218.179.187.34.bc.googleusercontent.com`;
- OTX: asn `AS15169 google llc`, United States.

`AbuseIPDB.lookup` returned None on a low score, dropping the whole response,
so the echo said "unknown to them". A model on a path with no tools, asked
to go deeper, then had no owner in front of it and supplied one from memory
("34.x is AWS"), dressed as WHOIS.

## Fix (`a90e18a`, Burhan's call: its own field, never a verdict)

- A lookup may return a `NetworkContext` beside its signal, or alone
  (`auspex/enrich/types.py`). It is never a signal: never synthesized, never
  recorded, so it cannot flip a verdict.
- AbuseIPDB returns it on every answer that names a network.
- The IOC echo shows it on its own line with its source, and does not say
  "unknown to them" about an address a source did name.
- The agent's `enrich_observable` result carries it as `network`.
- Tests: 8 new. Six failed before the fix; two pin behaviour that must not
  change (no network fields → no data; no network → "unknown to them"
  stays). 3/3 mutants caught. The route test pins the exact offending answer
  (tests/fixtures/enrich/b001_ip_owner_claim.json). Full gate green, 1323.

## Bounds, stated

- **Only AbuseIPDB supplies the owner.** OTX returns the ASN keyless and it is
  still dropped. A deployment without an AbuseIPDB key gets no owner, and the
  B-001 path is open again (TD-049).
- **The model still adds its own knowledge** where none was supplied: qwen
  named AS15169 as "to verify", and glm guessed "likely us-central1" and
  "likely California". That is the deferred item "the model fabricating
  incident specifics" (SESSION-RULES.md); it was not re-scoped.
- **Found and logged, not fixed:** B-005 (glm forges the `⟦DATA⟧` fence with
  invented platform lines on the conversational path) and B-006 (a follow-up
  on a no-signal IP calls it "clean").
- ACH evidence still words a no-claim enrichment as "(unknown to them — not
  benign)" (`auspex/ach/evidence.py:310-318`). It describes reputation claims,
  on a different surface, and was left as is.
