## 1. The fingerprint's blind spot — CONFIRMED, and it was one line from being fine

`canonical_spec` hand-lists the fields that constitute an action's identity, with
a comment saying a new `ActionSpec` field "must be considered here on purpose".
**Nothing enforced that.** Executed: a spec carrying a new declared field
(`min_plan="enterprise"`) fingerprints to `c6824a0e08a2985e…` — **byte-identical**
to the spec without it. An approver could be shown a changed declaration and the
execute-time re-check would call it unchanged.

The good news the probe also established: **coverage is complete today**, at every
level, which is what makes a structural guard cheap rather than a refactor.

| dataclass | declared fields | in canonical form | uncovered |
|---|---|---|---|
| `ActionSpec` | name, description, risk, scope, params, undo (+ dry_run/execute) | all six | **none** |
| `ActionParam` | name, type, description, required, enum | all five | **none** |
| `ActionScope` | system, writes, detail | all three | **none** |
| `UndoSpec` | description, restores, cannot_restore (+ handler) | all three | **none** |

Handlers stay out on purpose — we cannot detect a changed function *body*, and
S18's docstring is right that pretending otherwise would make the check look
stronger than it is. That is a deploy-integrity problem.

**Fixed:** `test_canonical_spec_covers_every_declared_field` asserts the dataclass
field sets against the canonical key sets at all four levels. **Proven to bite:**
adding a field to `ActionSpec` makes it fail, reverting makes it pass — run both
ways, not assumed. The decision about a new field is still a human's; it just can
no longer be made by forgetting.

## 2. A version bump told the analyst a lie — CONFIRMED, fixed

`FINGERPRINT_VERSION` has never been bumped. Executed what happens when it is:
every approved-but-unexecuted proposal refuses, which is correct, and says

> `annotate_observable has changed since it was approved (c6824a0e08a2… →
> a4870a6fe15d…) — re-propose it so a human approves what would actually run`

**The action did not change. Our hashing did.** Recoverable either way, but the
stated reason is false, and an analyst who re-reads the card hunting for the
change finds nothing. Same family as the S16/S17 lesson about surfaces that cannot
tell absence from failure.

**Fixed:** `matches_older_scheme(spec, stored)` re-hashes the *current, unchanged*
spec under each earlier version; if one matches, the declaration provably did not
move and the refusal says so with its own reason, `fingerprint_scheme_changed`.
Costs `FINGERPRINT_VERSION - 1` hashes and only on the refusal path. A spec that
genuinely changed still reports `spec_changed` — pinned by its own test so the new
branch cannot swallow the case it sits in front of.

**Found while fixing it (a second, quieter bug):** `version: int = FINGERPRINT_VERSION`
as a default argument binds **once at import time**, so the module constant and the
function's idea of it drift apart the moment anything changes it. Same trap in
`settlement.py`, which had imported the constant by value. Both now resolve at call
time. The test that caught this was failing for the right reason before the fix.

## 3. `executing` is a claim with no timeout — CONFIRMED, worse than described

Killed the app between the claim and the handler (the claim is exactly the UPDATE
`execute()` runs, so the simulation is the real statement). The row is then
permanently wedged:

```
execute  -> refused not_approved : proposal is executing, not approved
undo     -> refused not_executed : proposal is executing
reject   -> already_decided      : current status executing
final status: executing
appears in GET /api/proposals ? False
```

It can never be executed, undone, or rejected — **and it is invisible on the
approvals surface**, because `pending()` filters `status = 'pending_approval'`.
NEXT-SESSION.md predicted a stuck row; the part that was not predicted is that
**a human watching the queue sees the action simply vanish**. No error, no stuck
card, nothing to click. `undoing` has the identical shape.

**Not fixed this session** — a reaper is a durable job (the repo has the
SKIP LOCKED seam) plus a decision about what a reaped row becomes, and neither is
a Step-0-sized change. **TD-028.**

## 4. A failed execute leaves effects it denies — CONFIRMED, two defects

Forced a failure *after* the handler's INSERT landed (TD-025 names partial effects
as unwritten):

```
execute raised  : died after the write landed
proposal status : failed
result column   : {"error": "RuntimeError"}
notes WRITTEN by the dead execution: 1
undo -> refused not_executed: proposal is failed
```

**(a) The surface reports nothing happened while the note is really there.**
`failed` is a claim about the world, and here it is false.

**(b) The cleanup path exists and is locked behind a status check.** `undo`
requires `status = 'executed'`, so a `failed` proposal cannot be undone through
the API — even though `put_back` is keyed on `proposal_id` and would delete
exactly the orphaned row and nothing else (`builtin.py:136-141`). The handler
would work; the gate will not call it.

**Not fixed this session.** (b) looks like a one-word change and is not: allowing
undo from `failed` needs a decision about what the row becomes afterwards and
whether a `failed` proposal whose write never landed should report `undone`.
That is terminal-state semantics, and TD-025 already owns the neighbouring gap.
**TD-028.**

## 5. Tenancy — SOUND

The one angle that held. `pending()` filters `workspace_id` in SQL, and `stream()`
closes over `auth.workspace_id` once at connect time — one value, captured once,
never re-read from the request, so there is no path by which a later request could
swap it. Executed with two workspaces holding proposals simultaneously: workspace
A sees 0 of workspace B's rows.

**Not verified:** the `{"reconnect": ...}` frame at `STREAM_MAX_TICKS`. Reaching it
takes 600 real ticks at 1 s each, and nothing in the repo consumes this stream yet.
Recorded as still-undriven rather than claimed as working.

## 5b. Two identical calls file two proposals — confirmed; decided as correct

A model calling one action twice in a turn files two rows with identical
fingerprints and identical arguments. Both sit in the queue; approving both runs
the action twice.

**Recorded as correct rather than fixed.** A proposal is a request for a human
decision, and two requests are two decisions — deduping them would mean the
platform deciding that a second intent was a mistake, which is precisely the
judgement D-014 reserves for the human. What *is* a defect is that the surface
gives the approver no way to see they are being asked the same question twice.
That is a card-rendering concern, logged in **TD-028** rather than a fusion of
unrelated rows.
