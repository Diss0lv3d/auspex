## The measurement discipline — seventh session

The rule (assert the REASON, make controls ARITHMETIC) was applied up front
again. Every case in `probe_misbehaving_stream.py` asserts a property of its own
INPUT before running the loop — the truncated-argument case asserts the fragment
really is unparseable JSON, the two-call case asserts two distinct tool indices
are present, the reasoning-only case asserts zero content deltas. A surprising
result therefore cannot be blamed on a malformed script.

**It caught something this time, in my own work.** The strengthened anti-drift
test failed on its first run with `call 2 diverged`. The cause was the HARNESS:
`_tool_call_script` hardcoded `id="call_a"`, so a two-step streaming script
reused one id while the blocking fake used `call_a`/`call_b`, and the replayed
`tool_call_id` differed for reasons that were the script's fault. A version of
me that trusted the failure would have "fixed" `run_stream`. The discipline is
what made the failure attributable.

## FIXED — a turn the endpoint never answered reported that it answered

**Where:** `auspex/agent/loop.py` — `run`'s `if not calls` return and
`run_stream`'s `if not calls` `done` event, plus both step-cap exits.
**Harness:** `docs/probes/s26-step0/probe_empty_answer.py`.

Both paths ended a turn `final_answer` whenever the model call came back with no
tool calls. Neither asked whether an **answer** came back. Measured, pre-fix:

    [subject]  reasoning only, finish_reason=length
        analyst saw reasoning: 132 chars, content: 0 chars
        done(stop_reason='final_answer', text='', finish_reason='length')

    [control]  the SAME script with one content delta added
        done(stop_reason='final_answer', text='203.0.113.99 is malicious.', ...)

    => a turn with NO answer and a turn WITH an answer are reported
       with the same stop_reason: True

The terminal state is byte-identical to a complete answer's, differing only in a
`text` the route is told to persist as the assistant turn (NEXT-SESSION goal 2).
So *nothing happened* would be stored and rendered as *the answer is nothing* —
the same collapse as S25's `_resolve` fix, one layer up.

**Not an exotic endpoint.** The realistic path is a thinking model: reasoning
tokens count against `max_tokens`, so a model that thinks past its budget emits
reasoning deltas, `finish_reason="length"` and no content at all. STATE.md
standing follow-up 9 records that the default endpoint takes the **two-pass**
path, and the local dev model (`qwen3:14b`) is a thinking model.

**The fix.** `_terminal_reason(content, at_step_cap=...)` — one helper shared by
both paths, for the same reason `fold_stream_event` exists: they must not hold
two opinions about what counts as an answer. Blank (after `strip`) → the new
`empty_answer`. It outranks `step_cap` because both that and `final_answer`
claim *here is the answer*; nothing is lost, since `step` still carries whether
the cap was reached and the invocations still carry what was gathered.
`usage_refused` is untouched — it is the more specific fact.

**The fix lands on the blocking path too**, which is wired to nothing today.
That is the point: a fix on one side only IS the drift the shared helpers exist
to prevent.

**Proven.** Four regressions fail pre-fix on the right assertion. Neutralising
ONLY the emptiness check (`if False and not ...`) fails exactly those four
across the whole 1077-test suite — nothing else depended on the statement.
Whitespace is pinned separately, because `if not text` passes `"  \n "`.

## STRENGTHENED — the anti-drift pin reached one of three calls

`test_run_and_run_stream_compose_the_same_messages` compared
`calls[0]["messages"]`. Executed across a full capped turn
(`probe_drift_and_claims.py`), the two paths agree everywhere:

    calls: stream=3 blocking=3
    call 0: messages IDENTICAL   call 1: IDENTICAL   call 2: IDENTICAL
    => the shipped test compares 1 of 3 calls

So there is **no drift today** — but the pin could not have seen one. Only
`wire_specs`/`_initial_messages` are shared; the step loops are duplicated code.
The test now drives two tool steps plus the synthesis pass, compares all three
calls and whether tools were offered on each, asserts the call counts equal 3
first (a zipped comparison passes vacuously when one side is shorter), and
asserts the last call offers no tools so call 2 stays distinguishable.

**Proven to have teeth:** injecting one real drift — the streaming synthesis
pass offering tools, which is call 2 and therefore invisible to the old
assertion — fails this test and **only** this test across all 1077.

## CLEARED — and recorded as cleared

**1. `sealed[0]` does not assume anything unsafe.** The named worry was that an
exception mid-stream leaves `sealed` empty and `sealed[0]` raises `IndexError`
over the real fault. It cannot: the exception propagates out of the `async for`
before `sealed[0]` is reached. Measured both ways —

    raises_after_deltas:     events=['content','content'] then RAISED LLMError 500
    raises_after_tool_deltas: events=[] then RAISED LLMError 503, handler saw: []

The second confirms a tool announced but not sealed never runs, so a turn that
dies mid-stream has no half-executed side effects.

**2. Malformed tool calls degrade honestly.** Every misbehaving shape produces an
actionable `error` invocation and the turn continues:

| stream | result |
|---|---|
| ends mid-tool-call (`'{"ip": "203.0.'`, no finish) | `error: tool arguments were not valid JSON` |
| name present, no arguments at all | `error: missing required parameter(s): ['ip']` |
| two calls, the FIRST handler raises | both narrated; `boom` → `error: tool raised RuntimeError`, `lookup_ip` → `executed` |

The second tool still runs after the first raises, and both `tool` events reach
the caller — a failing provider costs one lookup, not the turn.

**3. The `fold_stream_event` extraction changed no behaviour.** The diff is a
mechanical move: identical statements, identical order, `accumulate_stream` now
delegating. Its two callers (`capability.py:129`, the client tests) are
unaffected, and `seal_stream_result` mutating in place cannot surprise anyone —
both call sites construct the `ChatResult` they pass.

**4. The claim-before-the-call is TD-030's ratified shape, not a new defect.**
Measured with the endpoint dying on call 2: `claims taken: 2, calls that produced
a result: 1` — charged 2 for 1 served. That is exactly what D-027 ratified and
TD-030 logs. It is also strictly **better** than the route's current behaviour,
which claims `1 or 2` up front regardless: a per-call claim means a turn that
dies on its first call is charged 1, not 2, and a loop making nine calls is
charged nine. **TD-035 does dissolve the moment the route moves to `run_stream`**,
exactly as its own path-to-fix predicted. No refund seam is needed or wanted —
the trap TD-035 names is adding a second place that knows how to count calls.

## What this leaves for the route (S26's goal)

- `done.stop_reason` now has four values. `empty_answer` means **do not persist
  `text`** — there is none. The route must render that as an honest failure, not
  as an empty assistant bubble.
- A mid-stream `LLMError` propagates OUT of `run_stream` after events have
  already been yielded. The route owns that contract: content the analyst has
  already read cannot be unsent, so the failure has to be appended, not
  substituted.
- Charging is already correct per call. The route must not re-add an up-front
  claim on top of `claim` — that is TD-035 rebuilt by hand.
