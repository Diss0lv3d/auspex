## FIXED 1 — the channel fix was a carry DROP, and drops lose things

**Read first.** S23 made a change of channel drop the carry. The carry is a
single shared slot, so *any* delta of the other kind evicts it — not only a
genuine pane transition.

**Then measured.** `probe_channel_carry.py`, controls first:

| case | expected | measured |
|---|---|---|
| C1 whole 12-word run, one content chunk | LEAKED | leaked |
| C2 split 6/6, two content chunks, no gap | LEAKED | leaked |
| C3 each half alone | CLEAN | clean, clean |
| **S** split 6/6, **one reasoning delta between** | ? | **clean — MISSED** |
| **S2** the mirror (reasoning \| content \| reasoning) | ? | **clean — MISSED** |

With C1–C3 sound, the only way S could trip is by carrying across the
interleave. It did not. A leak split across two chunks **of the same pane**,
separated by one delta of the other, walked through the rail — in both
directions.

**Is it reachable today?** Separately probed rather than assumed, because it
decides how the finding is written up, not whether it is fixed:

- The **two-pass path is immune by construction** — pass 1 feeds only
  `reasoning`, pass 2 only `content`, in sequential loops. No interleave is
  possible.
- The **default endpoint takes that two-pass path**: the persisted scorecards
  carry no `native_reasoning` key at all (probed:
  `select scorecard->>'native_reasoning' … → NULL` for all four rows, probed
  2026-07-15), so `_default_native_reasoning` resolves **False** for Scout.
- The one endpoint we have that emits a `reasoning` field, qwen3:14b, **does not
  interleave**: 361 reasoning deltas, then 32 content deltas, **1 switch**.

So the defect is **latent on the endpoints we have, not unreachable in general** —
the switch count is a property of the endpoint, and the platform's stated premise
is whatever OpenAI-compatible endpoint the customer brings. Worth noting that
`parse_sse_line` (client.py:285-287) emits `content` before `reasoning` when one
delta carries both, so a single such delta is already an interleave in our own
parser.

**Fix.** One carry **per channel** instead of one shared slot
(`_carries: dict[str, list[str]]`). Both guarantees hold at once and neither is
traded for the other: a run still cannot span two channels (the carries never
meet), and chunking stays invisible within a channel however the kinds
interleave.

**Proven pre-fix.** Neutralising only the carry lookup — restoring one shared
slot cleared on a change of channel — makes exactly the two new interleave tests
fail and leaves the other 16 green, including S23's boundary test.

Three regressions, and the third is the one that matters:
`test_an_interleaved_delta_of_the_other_kind_does_not_evict_the_carry`, its
mirror, and
`test_a_run_spanning_two_channels_still_does_not_trip_with_per_channel_carries`
— the over-correction control, because the boundary fix and the interleave fix
must hold **at the same time** and a test for each alone would let either be
traded for the other.

## FIXED 2 — the reachability pin asserted about the wrong statement

**Read first.** `undo` has *two* guards: a read-then-check at
settlement.py:530 (raises `not_executed`) and the atomic claim at :544
(`AND status = 'executed'`, raises `already_undone`). S23's pin asserts
`not_executed` — the pre-check — while its docstring credits the guarantee to
the claim and promises: *"If someone later loosens the undo claim, this fails
and points at the statement that has to be tightened with it."*

**Then measured**, by loosening one statement at a time:

| neutralised | pin result | meaning |
|---|---|---|
| the **claim** (:544) → `status IN ('executed','abandoned')` | **passes** (all 34 settlement tests pass) | the claim is **not guarded** |
| the **pre-check** (:530) | fails: `assert 'already_undone' == 'not_executed'` | the pre-check *is* guarded |

So the promise was false, and backwards: the pin guarded the racy statement and
left the atomic, load-bearing one bare. Nothing in the suite noticed the claim
disappearing.

**Fix.** `test_the_undo_claim_itself_refuses_an_abandoned_row` pins the claim by
the shape a claim exists for — a **stale read** saying `executed` while the row
is already `abandoned`, which is precisely what the pre-check cannot see. Only
`get` is faked; the claim runs against the real row.

**Proven pre-fix.** With the claim loosened it fails with
`Failed: DID NOT RAISE ExecutionRefused` — the undo proceeds onto the abandoned
row, which is TD-034 becoming reachable. TD-034's entry has been corrected: the
sentence claiming the old pin covered this was measured false.

## FIXED 3 — the refund fixture was opt-in, and opt-in did not hold

**Read first.** S23 added `_no_usage_residue` and three tests requested it. The
other thirty in the file did not. Every dev-login user shares one workspace —
`HARDENING_EMAIL` and `CHAT_EMAIL` are **the same string**, `analyst@auspex.dev`,
and the DB shows all 11 users on workspace `cce51a41…` — against an **hourly**
ceiling of 100.

**Then measured.** Counter cleared, then the file run with the three fixture
tests deselected: **29 unrefunded inference calls** from the remaining 30. The
file appeared clean only because the fixture `DELETE`s the whole row rather than
decrementing, and the three tests that use it happen to sit near the end. That
is the same incidental ordering S23 recorded as a risk — **moved, not removed**.

**Fix.** `autouse=True`. Safe at function scope, verified rather than assumed:
nothing in `test_chat_sse.py` asserts a limit or a usage count (all four matches
for `429|usage_counters|inference_calls` are inside the fixture itself), and the
limit assertions live in `test_hardening_surface.py`, which builds its own state
via `clean_usage` and inherits nothing. The three now-redundant explicit requests
were removed, since leaving them implies the fixture is opt-in.

**Measured after:** same deselection, residue **29 → 0**, file runtime 1.24s →
1.29s.

## ACCEPTED — a pass-1 leak is charged for the call it prevented (TD-035)

The TD-018 claim is `1 if native_reasoning else 2`, taken up front. S23's guard
means a pass-1 leak now ends the turn after **one** call while **two** were
claimed.

Accepted rather than reconciled. It over-charges, never under-charges; TD-030
already ratifies that a failed turn is charged in full; and `UsageLimiter` has no
refund path at all (`claim` is the only mutation), so fixing it means new API
surface on the exact code D-031 requires to be restructured — the claim must move
*inside* the loop, since a loop makes up to 9 calls against a claim of 1–2. It
dissolves there rather than being patched here. Logged as **TD-035**.
