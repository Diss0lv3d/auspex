## 1. What S32 built, in plain words

- **A connector** is now a described, versioned package: a `manifest.json`
  (what it is, what settings it needs, which hosts it may reach, what it can
  fetch and do) plus Python code. An author can write it in Python or in YAML,
  and both build to the identical manifest.
- **The SDK** (`sdk/`, installed as `auspex-sdk`, imported as `auspex_sdk`) is
  the kit an author uses: decorators, a typed settings object, an HTTP client
  that can only reach the declared hosts and supports certificate pinning,
  logs that hide secrets, a `build` command and a test bench that replays
  recorded HTTP exchanges.
- **A reference connector** (`examples/connectors/mock_siem/`, both forms)
  passes the test bench.
- **Connector actions become platform actions**: each one compiles into the
  same `ActionSpec` the approvals system already uses, so every connector
  write goes through an approval. The approval fingerprint now also covers
  the connector's id and its package hash (fingerprint version 2).
- **The catalogue**: an admin uploads a package into their workspace
  (`POST /api/connectors`); everyone in the workspace can list what is
  available (`GET /api/connectors`). A provider (MSSP) can offer a package to
  its own clients. Platform ("first-party") packages are added by a
  command-line tool and listed everywhere.
- **Bug B-026 is fixed**: an action call carrying an argument the action does
  not declare is refused when it is filed, and also at run and undo time.
- **Structural tests** prove the platform never loads connector code or YAML.

Nothing *runs* a connector yet. That is S33 (integrations and the Edge Agent).

## 3. Hunaiza's calls (product and security)

Made with Burhan's questions in hand; where the docs already answered, the
docs were followed; where they did not, Claude's suggestion was taken.

1. **D-071, provider connectors on client agents.** "Customer" in D-062 reads
   as a provider together with its clients, so a provider's offered connector
   may run on its clients' own agents, bounded by: the client admin chooses to
   use it, the agent checks the hash, it never runs on Auspex's
   infrastructure, and a provider offers only to its own clients.
2. **A certificate pin replaces the chain check.** A connector's TLS setting is
   one of: system trust; a pinned CA; or a pinned certificate hash, which
   trusts exactly that certificate and nothing else (so a self-signed on-prem
   SIEM is reachable safely). Turning TLS off is impossible to express.
3. The spec's decisions 1–11 (where the SDK lives, what the hash covers, the
   catalogue's tenancy, job kinds, and so on), listed in the spec.

## 4. Calls made during the build (rulings), with what each costs if wrong

**Before building**
- **R1: the core does not declare `auspex-sdk` as a dependency.** The name is
  not ours on PyPI, so declaring it invites a "dependency confusion" attack.
  `ci.sh` and the Dockerfile install `./sdk` explicitly instead. *Cost if
  wrong:* a developer running only `pip install -e .` must also install
  `./sdk`.
- **R2: TLS tests make their certificate with the `openssl` tool**, adding no
  Python dependency; the test fails (not skips) without openssl. *Cost:* a
  runner without openssl fails the gate.

**Manifest and packages (Tasks 2–3)**
- The "shared fetch needs a routing key" rule is checked per fetched item
  (`check_fetch_item`), since a manifest has no items. S33 must call it.
- Accepted refinements: an `undo_on_read` rule, `bad_name`/`bad_type` rule
  names, a 5 MB cap on both the upload and its declared contents, paths hashed
  in UTF-8 byte order.

**SDK runtime and build (Tasks 4–6)**
- A synchronous handler API (each command will run in its own process, D-062);
  `@connector(hosts=…)`; `load_config` / `Context.create`.
- **Plan defects fixed:** `commands.test`/`fetch` gained a required `handler`,
  and each action a required `execute` reference, because S33 must know what
  code to run and the YAML form must name it.
- The settings object (`ctx.config`) is built from the manifest for both
  forms; S33's runner must build it the same way.

**Compiling actions and the fingerprint (Task 8)**
- `compile_action` takes the `integration_id` (the job needs it).
- **Tool names fit the 64-character limit** model endpoints enforce:
  `MAX_TOOL_NAME = 64` is defined once, action names are capped at 38 so any
  legal 24-character prefix fits, and compilation refuses anything longer.
  *Cost:* authors with longer action names must rename (none exist).
- A connector's text shown to the model or approver is flattened to one line
  and capped.
- Approvals stored under the old fingerprint are refused with an honest
  "the scheme changed, re-propose" reason, never silently accepted.

**B-026 (Task 9)**
- **Refuse, never strip**, any argument the action does not declare: stripping
  would silently change what was approved.
- There is no HTTP route for filing proposals, so the refusal reaches the
  model in words through the agent loop's existing path.
- The same check runs before a stored request is executed or undone, and
  before the row is claimed, so nothing is left stuck half-run.
- The refusal names at most five keys, each shortened, so a hostile model
  cannot flood the text.

**The catalogue and routes (Tasks 10–11)**
- **One listing per connector id**: platform beats provider beats the
  workspace's own. Platform and provider registrations are never refused over
  a name a tenant already used, or any tenant could block them. *Cost:* a
  tenant's own package can be hidden behind a same-name offer (it stays
  stored; renaming shows it).
- Every version from the winning source is listed (S33 pins by hash).
- A client listing a provider's or the platform's package never sees which
  workspace or person registered it.
- The workspace and the registering user always come from the signed-in
  session, never from the upload form; `first_party` can never be set over
  HTTP.
- One new dependency, `python-multipart`, which FastAPI needs for uploads.
- No audit event for registration yet: the audited action list is fixed by a
  test, so adding one is its own decision (TD-068, for S33).

**Records (Task 13)**
- New debt: TD-066 (package bytes stored in Postgres), TD-067 (some invisible
  characters in connector text still pass), TD-068 (no audit event), TD-069
  (a build can include key files whose names do not start with a dot).

**Final review fixes (2026-10-27)**
- A secret placed in a URL path is now hidden in the form httpx writes it.
- The command-line tool refuses an oversize file before reading it.
- Two identical uploads at the same moment give one entry, not a false "bump
  the version" refusal.
- Key files in a package (TD-069) were logged, not refused, because a CA
  certificate file can be legitimate.

## 5. Small findings left on purpose (deferred minors)

None changes what a user gets today; each is a polish or a hardening for later.

- **Manifest:** some odd host and port forms are accepted (IPv4, single-label,
  leading zeros); a lone surrogate character crashes JSON output; a config
  field named `workspace_id` is accepted; the raw-size refusal reuses the
  description rule's name.
- **Packages:** directory entries skip the path check; FIFO/device entries
  count as files; error messages echo unbounded member names; `build_zip`
  sorts by text while the hash sorts by bytes; `ß`/`ss` collide under
  casefold.
- **SDK runtime:** one placeholder pattern and one host check are written in
  two places; the pin-mismatch error is not an `httpx.HTTPError`; private
  attributes can reach around the HTTP wrapper (it is not a sandbox; S33's
  agent is).
- **Build and harness:** namespace packages stay loaded after a build; the
  bench matches requests by method and URL only (headers are not asserted);
  some boolean-as-integer guards are untested.
- **Catalogue and routes:** the tenancy test uses a fixed connector id; the
  listing query could be written more simply; an unexpected upload-parse error
  reads as 422 rather than 500; D-071 holds two calls in one entry.

## 6. What S33 must pick up (also in `NEXT-SESSION-BE.md`)

- Dispatch runs `actions[].execute` and `commands.test`/`fetch.handler`.
- `check_executable` admits only the `auspex` system today; S33 must admit
  connector systems, and bind each approval to its `integration_id` (or never
  reuse a prefix).
- The Edge Agent's runner builds `ctx.config` exactly as the harness does,
  redacts stdout/stderr too, and is the real network sandbox.
- The agent decodes zip member names as CPython does and sorts by UTF-8 bytes
  when it re-hashes.
- The core's result check imports the SDK's validators instead of rewriting
  them, and calls `check_fetch_item`.
- Keep the zero-bytes pin test tied to the locked httpx version.
- Add a `connector.registered` audit event under a D-entry (TD-068).
